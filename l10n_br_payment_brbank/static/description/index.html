Brazilian Payment Providers: brbank (boleto and Pix)

Issue and follow boletos and Pix charges in several Brazilian banks through brbank, a Python library with one adapter per bank. This module is the Odoo face of the library: one generic payment provider (code = brbank) and one provider record per bank, so a new bank is data and a credentials screen, not a new module.

Banks delivered as providers (all disabled until configured):

  • Boleto: Banco Inter, PinBank, Sicoob, Sicredi, Banco do Brasil, Itaú, Bradesco, Santander, BTG Pactual, C6 Bank, Banrisul, Unicred, Caixa and Safra.
  • Pix (BACEN API, /cob and /cobv): Banco Inter, Banco do Brasil, Sicoob, Sicredi, Itaú, Bradesco, Santander and Efí.

What the module does:

  • One bank title per open installment of the invoice, each transaction tied to its installment (move_line_id of l10n_br_payment): issuing again never charges twice, and paying out of order settles the right installment.
  • Transaction states follow the canonical status of the bank: pending registration -> pending, registered -> authorized, settled -> done, written off -> canceled, rejected -> error. A transaction is only settled after the bank is queried: a webhook never settles anything by itself.
  • Fills the digitable line, bar code, Pix copy and paste and TXID that l10n_br_payment shows on the transaction, the invoice PDF and the portal.
  • Bank instructions (due date extension, rebate, protest, write-off) as records with the answer of the bank, offered only when the bank declares the capability, from the transaction or from the open installment of the invoice. What the bank accepts reaches the invoice: the due date of the installment, or a credit note for the rebate.
  • A generic webhook per provider, protected by a secret token, that stores the events and answers at once; the events are processed by a cron triggered immediately, which queries the bank.
  • A reconciliation cron for every brbank provider, as the safety net of the webhooks.
  • Credentials readable only by system administrators; certificates go to the library only in memory; logs and stored bank answers are masked by the library (no name, document, address or PDF of the payer).

The library is asynchronous; the module calls it through a single bridge that runs each call in a dedicated, short lived event loop.

Configuration

  1. Install the brbank Python library in the Odoo environment (pip install "brbank>=0.0.12"). It needs Python 3.10 or later. Version 0.0.12 is the minimum: it brings the Santander, Itaú and Bradesco settings described below (the manifest only names the package, so the version is not checked at install). For Sicoob, the document kind (codigo_especie_documento) is the acronym, for instance DM, and no longer a number.
  2. Go to Invoicing > Configuration > Bank Connections and create the connection of the bank account (see the module l10n_br_bank_connection): adapter, environment (test uses the bank sandbox), CNPJ, credentials, the JSON of Extra Settings and Extra Secrets (Fill settings template lists the keys), and the consent at the bank where the adapter needs one (BTG). The webhook URL to register at the bank is on the connection.
  3. Go to Invoicing > Configuration > Payment Providers and open the provider of the bank (for instance Sicoob (Boleto) or Pix Itaú): the bank adapter (and the Pix profile) are already set by the data; choose the Bank Connection. One connection can serve several providers.
  4. Set the provider to Test Mode or Enabled and choose its journal in the Configuration tab. The provider refuses to leave Disabled without a connection of the same adapter, or while a required key is missing. Test or production is decided by the environment of the connection.
  5. In the payment mode (Invoicing > Configuration > Payment Modes), tick Generate boletos on invoice? and choose the provider. The payment mode shows what the bank supports.
  6. To send rebates, choose the Rebate Account of the provider: the rebate is refused before reaching the bank while it is empty.

The webhook URL to register at the bank is the one of the connection; the route /payment/brbank/webhook/<provider>/<token> is kept as an alias. Keys typed as a function in the library (gerar_nosso_numero, ao_renovar_refresh_token) never go in the JSON: the provider and the connection serve them.

Notes per bank:

  • BTG Pactual: the API only accepts tokens of the authorization code flow. Use Connect on the bank connection (or paste a refresh token in Refresh Token). The bank may return a new refresh token at each renewal and invalidate the old one: the connection saves it at once, in a database transaction of its own, so an error or a rollback of the operation never loses it, and the renewals of the workers are serialized by a lock of the database. A refresh token unused for more than 10 days expires and the consent must be done again. Use each BTG credential in one database only. Fill dias_expiracao (days after the due date until the title expires), or the bank refuses titles without an automatic write-off term.
  • Caixa: there is no public test environment, so the connection refuses the test environment. Use production and validate with a title of low amount. documento_beneficiario is a secret key (Extra Secrets).
  • C6 Bank: the Pix key must be a random key (EVP); the bank silently issues a boleto without Pix with any other kind.
  • Itaú: bolecode (hybrid boleto) is on by default and needs the Pix key. When the bank delivers a separate credential for the Bolecode, fill bolecode_client_id and, in Extra Secrets, bolecode_client_secret, bolecode_certificado_pem and bolecode_chave_pem. A protest needs dias_protesto; without it the instruction is recorded as rejected.
  • Santander: the Pix key needs tipo_chave_pix (EMAIL, CPF, CNPJ, CELULAR or EVP); workspace_id is the billing workspace created at the bank. Set webhook_ativo to true before registering the webhook URL in the workspace: without it the webhook is refused.
  • Bradesco: documento_beneficiario is a secret key (Extra Secrets). With hibrido (boleto with QR code) the bank takes no protest by instruction.
  • Banrisul: the provider sends the 8 free digits of the nosso numero and the library adds the check digits.
  • Unicred: api_key and the two webhook keys go in Extra Secrets.
  • Safra: the bank declares no capability (no write-off, instruction, PDF nor webhook): titles are followed by the reconciliation cron only.

Nosso numero: for the banks where the issuer chooses it (Banco do Brasil, Bradesco, Itaú, Santander, Banrisul, Caixa and Safra) the provider creates its own sequence (Nosso Numero Sequence) at the first title, starting after the numbers already registered by it. The number is taken before the first call to the bank and kept on the transaction (Nosso Numero Sent), so a retry sends the same one, and a number is never given twice. When the sequence passes the digits of the bank (Itaú 8, Banrisul 8, Safra 9, Banco do Brasil 10, Bradesco 11, Santander 12, Caixa 15), the registration stops with an error instead of cutting the number: agree with the bank on a new wallet or agreement.

Only users of Administration / Settings see and edit the credentials (on the connection). The webhook token travels in the URL: mask it in the logs of the reverse proxy.

Crons:

  • Boleto brbank: reconcile titles with the banks, every 30 minutes. Lengthen it only when the webhook of every bank in use is validated in production.
  • Boleto brbank: process bank webhook events, triggered by every webhook call and every 10 minutes as a fallback.

Usage

Issuing:

  • Post a customer invoice whose payment mode generates boletos with a brbank provider: one transaction per open installment is created and registered at the bank. Generate boletos again only issues the installments without a live title.
  • If the bank is unavailable, the transaction stays in draft with the reason and the reconciliation cron registers it later with the same idempotency key. If the bank refuses the data, the posting stops with the reason, naming the missing customer fields.
  • A title the bank has not confirmed yet (the Itaú Bolecode may answer “in progress”) stays pending, takes no instruction and is not shown to the customer, until the reconciliation cron reads it as registered.
  • The portal also offers the boleto PDF when the bank provides one.

Following up, in the transaction:

  • Check at the bank reads the title back and applies its status. The Capture button of payment does the same, and Void writes the title off.
  • Bank instruction sends a due date extension, a rebate or a protest; Write off at the bank cancels the title. The buttons only show when the bank declares the capability; a command the bank refuses stays recorded as rejected, with the reason.
  • For BTG Pactual, the Refresh Token of the provider changes by itself after the calls to the bank: the provider keeps the last token the bank returned.
  • Invoicing > Customers > Boleto Instructions lists every instruction, and Invoicing > Configuration > Payments > Bank Webhook Events every event received (managers only).

From the invoice: the Receivables tab has a Bank instruction button on each open installment with a registered boleto, offering only what the bank accepts. After the bank accepts:

  • Due date extension: the due date of the installment and of the invoice change.
  • Rebate: a credit note without taxes and without a fiscal document is posted on the Rebate Account of the provider and reconciled with the installment. If Odoo cannot post it, the instruction stays accepted, the reason goes to the invoice and an activity asks the salesperson (or the sender, when the salesperson has no access to invoices) to do it by hand.
  • Write-off: the invoice only receives a message. The title remains open, since the customer still owes the amount.

Santander: a boleto the bank reports as written off, with no write-off sent from Odoo, is not canceled: it may have been paid by Pix. The transaction stays open with Review Needed filled, and the invoice receives a message and an activity.

Return files (CNAB): a module that reads a return file of an account that also uses the API can call payment.transaction._brbank_notify_cnab_occurrence( nosso_numero, company): the transaction is found by its nosso numero and read back from the bank, so the file and the API never settle the same title twice.

Known issues / Roadmap

  • Only Sicoob (boleto and Pix) has been validated in a bank sandbox, the public one of Sicoob, which checks the requests against the API contract but keeps no state; the production OAuth, mTLS and scopes are still unproven. All the other adapters have validado_sandbox = False: they were built from public documentation. The provider form and the payment mode warn about it. Test each bank with low amounts before production.
  • The manifest names the brbank package without a version (a specifier there breaks the import check), so the minimum version is not enforced at install.
  • The registration runs in the transaction that posts the invoice. If that transaction is rolled back after the bank answered, the bank keeps the title; the next attempt sends the same idempotency key (Pix answers Duplicado and the title is read back), but a boleto bank that does not deduplicate by our reference may keep an orphan title. The nosso numero is kept on the transaction, so a retry of the same transaction sends the same number; a transaction undone by the rollback takes a new number on the next attempt (the sequence never gives a number twice).
  • Webhooks are only parsed for the banks whose adapter declares them (Inter, Sicredi, BTG Pactual, C6 Bank, Unicred and the Pix profiles); the others rely on the reconciliation cron.
  • The digits of the nosso numero of each bank are a map in the module (NOSSO_NUMERO_DIGITS), checked by a test against the adapters that take gerar_nosso_numero; the library does not publish them in a uniform way.
  • BTG Pactual: the authorization code flow (consent at the BTG Id) is done outside Odoo. Two calls renewing the same refresh token at the same time (two workers) may leave one of them with a token the bank already replaced.
  • Caixa has no test environment: the provider cannot use the test mode.
  • The webhook events are processed by ir.cron with an immediate trigger, not by queue_job, so the module adds no dependency; move to queue_job if a bank sends large volumes.
  • The CNAB bridge is a hook (_brbank_notify_cnab_occurrence): no return file module calls it yet.
  • The brbank providers are left out of the online checkout: the redirect and token flows of payment are not implemented for them.
  • The credentials are stored in the database, restricted to the settings group; a vault (Vault, KMS) is not supported yet.
  • The reconciliation cron queries each open title; banks with batch queries or movement statements could be read in one call per account.
  • No alert yet for certificates close to expiry.
  • The provider records use the module icon; the logos of the banks are not shipped.
